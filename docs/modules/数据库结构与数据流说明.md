# 数据库结构与数据流说明

> 定位：v4.1 结构导览，用于建立全局认知——**库长什么样、用什么实现、数据怎么流动**。
> 本文讲结构与数据流，不含 SQL 细节；施工依据见 `00_数据库开发书_最终版_v4.0.md`，对外接口见 `../01_需求与总体设计/api_contract.md` §8。

---

## 1. 一句话说清楚：我们的数据库是什么

**就是一个文件。**

可与 Excel 工作簿对照：

- 它也是**一个文件**（我们的是 `DNA_/data/db/medical_archive.db`）；
- 里面也有多个**工作表**（数据库里叫「表」，我们有 10 张）；
- 每张表有固定的**列**（这一列只能填日期、那一列只能填数字，填错了不让保存）；
- 表和表之间可以**互相引用**（就像一个单元格写「见 Sheet3 第 5 行」）。

和 Excel 的最大区别：**Excel 管不了你乱填，数据库管得了。** 我们医疗数据不能乱，所以用数据库。

## 2. 用什么实现：SQLite

| 问题 | 答案 |
|---|---|
| 用的什么数据库软件？ | **SQLite**——注意，它不是一个要安装的服务器软件，而是一个「读写字文件的程序库」 |
| 要不要装东西？ | **不用**。Python 自带 `sqlite3` 模块，写三行代码就能打开我们的库 |
| 数据存在哪？ | 就一个 `.db` 文件，拷到 U 盘就是备份，删了就是没了 |
| 谁在用它？ | 微信聊天记录、手机通讯录、Chrome 的 Cookie，底层都是 SQLite。它全世界装机量最大 |
| 我们为什么选它？ | 单机桌面软件（Flet 做的 DNA 档案系统），不需要「多台电脑共用一个服务器」，SQLite 正好，而且零配置 |

打开我们的库，只需要：

```python
import sqlite3
db = sqlite3.connect("DNA_/data/db/medical_archive.db")
```

就这样，没有密码、没有端口、没有服务要启动。

## 3. 整个库的地图：10 张表，4 个组

整个库按职责分为**四个表组**（v4.1 起没有账号体系，`users` 表已删）：

```
┌─────────────────────────────────────────────────────┐
│  ① 档案封面柜（1 张表）                               │
│     archive_records —— 每份档案的封面页               │
│     （姓名、性别、身份证号、建档日期……）               │
│                                                     │
│  ② 表格骨架柜（3 张表）★ 整个库的心脏                │
│     sections —— 大标题（"一、患者基础信息"这种）       │
│     fields   —— 每一个要填的空（"既往患病史："）       │
│     options  —— 每个空旁边的候选项（"高血压、糖尿病…"） │
│                                                     │
│  ③ 填写结果柜（1 张表）                               │
│     answers —— 患者实际勾了什么、填了什么              │
│                                                     │
│  ④ 配套设施柜（5 张表）                               │
│     icd_codes          —— 国家疾病编码字典（35,867 条）│
│     dna_sequences      —— 编码成的 DNA 序列（ATCG）   │
│     decode_records     —— 解码记录与纠错日志          │
│     user_activity_log  —— 谁干了什么（操作日志，无账号）│
│     schema_meta        —— 贴在柜子上的版本标签        │
└─────────────────────────────────────────────────────┘
```

一句话记住：**②是「问卷的题目」，③是「患者的答案」，①是「谁在做这份问卷」，④是「配套设施」。**

## 4. 最核心的设计：表头 → 空 → 选项（三级结构）

这是本库最核心的设计，用**体检登记表**类比：

一张纸质登记表上有：

- 大标题：「既往史 / 家族史」（→ 存在 `sections` 表）
- 空格：「既往患病史：____」（→ 存在 `fields` 表）
- 空格旁边的备注：「可多选：高血压、糖尿病、冠心病……」（→ 存在 `options` 表）

**为什么要连「表头」都存进数据库？** 因为前端界面不用写死。表头改了名，或者加了一个空，界面自动跟着变——**改文档 = 改数据库记录，不用改程序代码**。这就是「表头即骨架」的意思。

三张表长这样（示意）：

**sections（8 行）**

| id | section_key | name_cn | level | 父节点 |
|---:|---|---|---:|---|
| 2 | storage | 存储部分 | 1 | — |
| 3 | past_and_family_history | 一、既往史与家族史 | 2 | storage |

**fields（16 行，全部是枚举型）**

| id | field_key | 空名 | 类型 | 必填 |
|---:|---|---|---|---:|
| 1 | past_medical_history | 既往患病史 | 多选 | 是 |
| 9 | smoking_history | 吸烟史 | 单选 | 是 |

**options（要挂几千行）**

| id | option_key | 中文名 | 挂在哪个空下 | 国家编码 |
|---:|---|---|---|---|
| 101 | icd_e11_900 | 2型糖尿病 | 既往患病史 | E11.900 |
| 102 | family__hypertension | 高血压 | 家族史 | I10.x00 |

注意 `options` 里那个「国家编码」列：候选项不是随意定义的，很多直接**对上了《疾病分类与代码国家临床版 2.0》这本国家字典**（就是项目根目录那个 xlsx，35,867 条）。这样我们勾的每一个病，都查得到官方编码。

## 5. 一次填表，数据是怎么走的

**场景：医生给小明的档案勾了「既往患病史：高血压、哮喘」和「过敏原：尘螨」。**

第 1 步：界面从库里读题目和选项（读 ② 组三张表）；
第 2 步：医生勾选；
第 3 步：保存——往 `answers` 表里写**三行**（注意，勾两项 = 两行，不是一格塞两个）：

| record_id | field_id | option_id | value_num | 含义 |
|---|---:|---:|---|---|
| ARCHIVE_20261113_001 | 1 | 57 | | 既往患病史 = 高血压 |
| ARCHIVE_20261113_001 | 1 | 63 | | 既往患病史 = 哮喘 |
| ARCHIVE_20261113_001 | 6 | 71 | | 过敏原 = 尘螨 |

看规律：
- **勾选项** → 存 `option_id`（指向 ② 组里第 57 号选项）；
- **填数字/文字** → 直接存值（`value_num` / `value_text` / `value_date`）；
- 数据库有一条铁规矩（CHECK 约束）：**勾了选项就不许再填值，填了值就不许勾选项**，二选一，防止脏数据。（我们的 16 个空全部是枚举型，实际走的全是「勾选项」这条路；值列是留给以后万一出现自由填写的空用的）

第 4 步：点「生成 DNA 存档」→ 这份档案的全部答案被序列化、加密、编码成一长串 `ATCGATCG…`，存进 `dna_sequences`。以后解码出错纠了哪一段，记在 `decode_records`。

**为什么一项勾选要单独占一行？** 为了以后好统计。比如「本月所有档案里，勾了哮喘的有多少份」——一行一勾，一句话就能查；要是塞在一个格子里（"高血压,哮喘"），就得拆字符串，又慢又容易错。

## 6. 三个易混淆点

**Q1：候选项为什么存数据库，不直接写在界面代码里？**
三个原因：① 要和国家字典 ICD 对账，勾的每个病都能查到官方编码；② 选项要经过审核（`reviewed_by` 列记录谁审的），医学词条不能拍脑袋；③ 加选项 = 插一行数据，不用发新版本软件。

**Q2：以前的老版本为什么被推翻了？**
老版本（v1~v3）把「题目」和「答案」混在一个 60 格的大字典里，用「键-值」对存，像一个巨大的 Excel：第一列写名字，第二列写值。问题是谁也管不住谁——同一个字段三处叫法不一、疾病分类自造 8 类跟国家 22 章对不上。新版本把「题目」和「答案」**分开存放**（②组 vs ③组），题目唯一、答案引用题目，矛盾就消失了。这就是 v4.0「重塑」的全部含义。

**Q3：「阴性体征」为什么不用填？**
勾了阳性（比如"皮疹"）才有信息量；"没有皮疹"这种阴性描述，直接由系统按阳性取反显示，不用人工再勾一遍。所以它在库里标了 `is_required = 0`（可以不填）。

## 7. 术语对照（10 个词，每个一句话 + 我们的例子）

| 词 | 意思 | 我们库里的例子 |
|---|---|---|
| 表（table） | 一张有固定列的表格 | `fields` 表 |
| 行（row） | 表里的一条记录 | `fields` 里的「既往患病史」那行 |
| 列（column） | 记录的一个属性 | `fields.name_cn`（空的中文名） |
| 主键（PK） | 每行的身份证号，不许重复 | `answers.id` |
| 外键（FK） | 指向别的表主键的「引用」，填错会被拒绝 | `answers.field_id` → `fields.id` |
| 唯一（UNIQUE） | 这一列不许有重复值 | `fields.field_key` |
| CHECK | 门卫规则，不满足就拒绝写入 | 「勾了选项就不许填值」 |
| 索引（INDEX） | 给常用查询建的目录，查得快 | 按「档案号」查答案的目录 |
| 幂等 | 同一段脚本跑一百遍，结果和跑一遍一样 | 我们的建表脚本 |
| 事务（transaction） | 把几步写入捆成一个包，要么全成、要么全不算 | 同一次随访的 4 个字段一起存 |

## 10. 全文浓缩成五句话

1. 我们的数据库 = **一个 `.db` 文件**，用 Python 自带的 SQLite 读写，不用装任何软件。
2. 库里 10 张表，核心思想是**三级结构**：表头（`sections`，8 行）→ 空（`fields`，16 行，全枚举）→ 选项（`options`）。
3. 患者填的内容进 `answers`，**一个勾一行**，勾选存引用、填值存数值，门卫规则保证不存脏数据。
4. 选项很多直接对上**国家 ICD 字典**（35,867 条），勾的每个病都有官方编码。
5. 档案最终编码成 **ATCG 序列**存进 `dna_sequences`——这就是整个项目「DNA 存储医疗档案」的落点。
