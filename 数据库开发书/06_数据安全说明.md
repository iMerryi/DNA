# 数据安全说明

> 项目：DNA 医疗档案系统　|　范围：数据库层（`data/db/medical_archive.db`）及其上下游
> 本系统存储儿童健康档案，属于**个人敏感信息（医疗健康数据）**，按最高标准防护。

---

## 1. 数据资产与风险识别

| 资产 | 敏感级别 | 主要风险 |
|---|---|---|
| 档案身份字段（姓名、身份证号、住址、父母电话） | 高 | 隐私泄露、身份冒用 |
| 档案内容（病史、过敏史、体征） | 高 | 医疗隐私泄露 |
| DNA 序列与密钥哈希 | 高 | 序列被还原明文 |
| 明文密钥（若有） | 极高 | 直接导致加密失效 |
| 上传的原始文档（docx/pdf） | 中 | 与档案同级别的隐私内容 |

---

## 2. 存储安全

### 2.1 密钥不落库

`dna_sequences` 表只存 **`key_hash`（密钥哈希）**，不存明文密钥。密钥由用户身份信息派生，仅在编解码瞬间存在于内存。

### 2.2 DNA 编码本身即一层防护

- 档案内容经 XOR 加密 + DNA 碱基映射后才落库，`dna_sequences.dna_sequence` 不是明文；
- **已知风险**：`dna_sequences.original_text`（编码前明文）与 `decode_records.decoded_text`（解码原文）目前以明文存储，用于二次编码比对与纠错审计；这两列与身份列同属高危资产，发布版应改为不存明文或改为加密副本，至少不得随库文件外发/提交到仓库；
- 载荷用 `json.dumps(..., ensure_ascii=True, sort_keys=True)`：纯 ASCII、确定性输出，便于完整性比对与纠错。

### 2.3 数据库文件保护

- 数据库文件位于 `data/db/`，不属于任何可执行目录；部署文档要求该目录不对外网开放；
- 建议后续在发布版中开启 SQLCipher（对库文件整体加密），当前单机演示版以文件权限 + 目录隔离为基础防护。

## 3. 访问控制

1. **应用统一入口**：所有读写必须经 `DataStore` 模块，UI/AI/编解码模块不得自行打开数据库连接或操作 db 文件（架构级访问控制）；
2. **最小权限**：`DataStore` 对外只暴露契约方法（save/load/update/delete/list 等），不暴露原始 connection 之外的执行通道；
3. **词典与字典只允许登记修改**：`field_key`、`term_key` 一经入库不可改名；新增字段走 `add_field_definition()` 并需 PM 审核，禁止业务代码临时造 key——从源头防止数据被写入语义错乱的字段；
4. **账号与数据归属（v3.0 新增）**：
   - `users` 表区分档案归属，`archive_records.owner_id` 外键关联，`list_records` 支持按归属过滤；
   - 密码只存哈希：`pbkdf2_hmac('sha256', ...)` 20 万次迭代 + 16 字节随机盐，格式 `pbkdf2$iters$salt$hash`，比对用常量时间函数（05 §13.1 有现成实现）；
   - 停用账号置 `is_active=0` 而非物理删除，拒绝登录但保留归属关系；
   - **操作日志**：10 类关键动作全量落 `user_activity_log`，`action` 受 CHECK 约束限定枚举，日志只增不改；
   - **如实边界**：`load_record`/`update_record`/`delete_record` 不校验归属，本系统的账号定位是**数据归属区分，不是对抗性权限控制**——答辩与文档中不得表述为"权限控制"。

## 4. 写入防护：让脏数据进不来

这是本设计最核心的安全机制——**用数据库约束做最后一道防线**，即使上层代码有 bug 也写坏不了数据：

| 防线 | 机制 | 防住什么 |
|---|---|---|
| 外键约束 | `PRAGMA foreign_keys = ON`（每次连接）+ 9 处外键（04 脚本，v3.0 增加归属与日志外键） | 指向不存在的档案/词条/用户的孤儿数据 |
| 字典外键 | `record_entries.field_key → field_definitions` | 未登记字段名、拼写漂移 |
| 唯一约束 | `UNIQUE(record_id, field_key, seq)` 等（`seq` 为 NOT NULL） | 同一槽位重复写入、NULL 绕过唯一约束 |
| 枚举规范 | `gender`、`result_en`、`source`、`payload_mode`、`role`、`action` 等列级 CHECK 兜底；血型/缓急等键值字段由应用层 R3 校验 | "男/male/M" 混存、日志临时造 action |
| 业务校验 | R1/R4/R5：写入前校验 field_key、同步 value_num、seq 连续；用户名统一小写判重 | 类型错乱、序号断档、`Tom/tom` 双账号 |

> 特别说明：`PRAGMA foreign_keys` 是**连接级**设置，只在建表脚本里写一次是无效的——`DataStore._connect()` 每次建立连接都必须重新执行，这一点已写入代码规范与验收标准（T9：手动插入不存在的 record_id 必须被拒绝）。

## 5. 删除策略：软删除 + 审计链

1. **档案级软删除**：删除只置 `archive_records.is_deleted = 1`，数据仍在库中，满足医疗档案的留痕要求，可恢复、可审计；
2. **条目级物理覆盖**：内容条目"写入即覆盖、删除即物理删"，与唯一约束配合避免"删后重加撞槽位"；条目变更通过 `updated_at` 留痕；
3. **编码—解码全链路可追溯**：`dna_sequences` 保留历史版本（`is_valid=0` 不删除），`decode_records.correction_log` 记录每次纠错过程，`payload_version` 记录载荷格式版本——任何一次编码/解码都可回溯；
4. **物理删除受外键保护**：`dna_sequences` 不设 `ON DELETE CASCADE`，直接删除有 DNA 记录的档案会被外键拒绝；确需销毁时按 05 §5 的依赖顺序（解码记录 → DNA 序列 → 档案）显式清理，避免审计链被误删。

## 6. 备份与恢复

- `backup_database()`：`VACUUM INTO` 生成一致性快照（不锁写、体积紧凑），备份文件带日期存放于 `data/backups/`；
- `restore_database()`：恢复后自动执行 `PRAGMA integrity_check` 并核对 `schema_meta` 结构版本；
- 建议节奏：每次大批量导入/迁移前强制备份；日常每日一次。
- v1 → v2 迁移全程保留 `*_v1` 只读表一个版本周期，病症迁移先入 `legacy_disease_staging` 暂存、人工审核后合并，**防止脏数据污染 236 条标准词典**。

## 7. 隐私合规要点

依据《中华人民共和国个人信息保护法》《数据安全法》对敏感个人信息的要求：

1. **最小必要**：仅采集《10.17 医疗信息框架》定义的 60 个字段，不多采；
2. **目的限定**：数据仅用于本系统档案管理与 DNA 冷存储演示，不做对外共享或二次利用；
3. **去标识化设计**：列表接口 `list_records` 只返回身份列；DNA 载荷可切换 `canonical_en` 模式减少冗余内容；
4. **知情同意**：录入界面明示数据用途（儿童健康档案管理 + 本地演示存储），不上传任何数据到外部服务器——**本地 SQLite + 本地 Ollama 的架构本身就保证了数据不出机**；
5. **演示数据脱敏**：代码仓库、答辩材料中的示例档案一律使用虚构姓名与虚构证件号。

## 8. 安全会 Checklist（验收参照）

| # | 检查项 | 期望 |
|---|---|---|
| S1 | 库文件中搜索明文密钥 | 不存在（只有 key_hash） |
| S2 | 插入孤儿条目（record_id 不存在） | 被外键拒绝 |
| S3 | 插入未登记 field_key | 被外键拒绝 |
| S4 | 软删除后 list_records | 不可见；load_record 返回 None |
| S5 | 任一写操作中途崩溃 | 无"半条档案"（事务回滚） |
| S6 | backup → restore 后 integrity_check | 返回 ok，记录数一致 |
| S7 | 仓库/文档中的示例数据 | 全部虚构，无真实个人信息 |
| S8 | 库文件中搜索明文密码 / users.json 导入后 | 不存在明文；库内只有 pbkdf2 哈希 |
| S9 | 插入非法 action / 非法 role | 被 CHECK 拒绝 |
| S10 | 日志写入故意失败（如表被锁） | 主流程不受影响，且不产生静默丢失（WAL + 同连接） |
